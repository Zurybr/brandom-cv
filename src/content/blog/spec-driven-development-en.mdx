Andrej Karpathy coined "vibe coding" in February 2025. A year later, he admitted the era is ending. The replacement? **Agentic engineering**: orchestrating AI agents against detailed specifications with human oversight, not prompting your way through code.

This shift has a name: **Spec-Driven Development (SDD)**. And it is fundamentally changing how production software gets built.

![Spec-Driven Development: from Kiro to Spec Kit and Tessl](/images/blog/spec-driven-development/hero.jpg)

## The Problem with Vibe Coding

Vibe coding works for prototypes. It fails at scale. Here is why.

**Context decay.** AI agents are stateless. When you start a new chat, you lose every decision made in the previous one. The agent forgets why you cleaned data a certain way, and the next update silently introduces a different approach.

**No shared conventions.** Without structure, teams end up with five different patterns for the same operation. One developer uses Repository pattern, another puts ORM calls directly in controllers. Neither is wrong, but the inconsistency compounds.

**No audit trail.** Conversations with AI agents are ephemeral. When something breaks three months later, there is no record of why a decision was made or what alternatives were considered.

**Security blind spots.** Research from SonarQube found over 70% of code generated by some LLMs contained BLOCKER-severity vulnerabilities. Unit tests catch function-level bugs. They do not catch architectural violations, API contract drift, or cross-service security anti-patterns.

The numbers are stark: by February 2026, researchers counted over 110,000 surviving AI-introduced issues in production repositories. Vibe coding ships features fast, but it ships problems faster.

## What Is Spec-Driven Development?

SDD treats specifications as executable contracts, not passive documentation. The spec becomes the single source of truth that both humans and AI agents work against.

A spec is not a PRD. PRDs are written for humans who can interpret ambiguity. SDD specs are written for AI agents that will fill ambiguity with wrong assumptions. The spec explicitly defines outcomes, scope boundaries, constraints, prior decisions, task breakdowns, and verification criteria.

### The Three Levels of SDD

Not all SDD is created equal. Birgitta Böckeler from Thoughtworks identifies three distinct levels:

![The three levels of SDD: Spec-First, Spec-Anchored, and Spec-as-Source](/images/blog/spec-driven-development/sdd-levels.png)

**1. Spec-First.** A well-crafted spec is written before implementation and used to guide the AI agent. After the feature ships, the spec may or may not be maintained. This is the entry point. Most teams start here.

**2. Spec-Anchored.** The spec lives alongside the code and evolves with it. When requirements change, the spec is updated first. Automated tests bridge documentation and implementation, integrated into CI/CD to keep both synchronized. This is where most engineering teams should aim.

**3. Spec-as-Source.** The spec IS the source code. Humans never edit generated files. Changes to the spec automatically trigger code regeneration. This is the most ambitious form, and the most risky given LLM non-determinism. It echoes the promises (and failures) of Model-Driven Development from the early 2000s.

### How SDD Relates to TDD and BDD

SDD does not replace TDD or BDD. It operates at a different layer.

| Dimension | TDD | BDD | Vibe Coding | SDD |
|---|---|---|---|---|
| Primary artifact | Unit tests | Given-When-Then scenarios | Natural language prompts | Executable specifications |
| Scope | Function correctness | Cross-functional behavior | Full application | System-wide architectural contracts |
| Validation | Automated test suites | Workshop documentation | Manual review (if any) | Build fails on spec divergence |
| AI governance | None | None | None | Constitutional constraints |

Use TDD for implementation verification. Use BDD for cross-functional collaboration. Layer SDD on top for architectural governance.

## The SDD Workflow in Practice

A typical SDD workflow follows these stages:

![Agent context files overview: Memory Bank vs Specs](/images/blog/spec-driven-development/sdd-overview.png)

### 1. Define the Constitution

Before writing any feature spec, establish the project's foundational principles. This "constitution" typically includes:

- **Mission**: Why are we building this? What are the key goals?
- **Tech Stack**: Technical decisions, deployment processes, and tooling.
- **Roadmap**: Phased plan, continuously updated as the project evolves.

The constitution acts as guardrails. Every feature spec, every plan, every task must align with these principles. This prevents agents from making architectural decisions that contradict the project's foundation.

### 2. Write the Feature Specification

Focus on **what** and **why**, not **how**. A good spec includes:

- **Outcomes**: Not "build an auth flow" but "a user can sign up with email/password, receive a verification email, and log in without error."
- **In-scope and out-of-scope boundaries**: Explicitly state what is NOT included. Agents expand scope if you do not close the door.
- **Constraints**: Existing tech stack, API limits, performance requirements.
- **Decisions already made**: If the database schema is chosen, say so. Agents that do not know a decision has been made will make their own.
- **Task breakdown**: Discrete sub-tasks let agents work in parallel and verify incrementally.
- **Verification criteria**: What tests pass, what edge cases are handled, what the verifier checks against.

### 3. Plan and Validate

Translate the spec into a technical implementation plan. Choose the tech stack, define the architecture, and break down the work. Then validate the plan by having a second agent review it with fresh context.

### 4. Implement

Execute the plan task by task. Each task is small enough to verify independently. The spec is the source of truth throughout.

### 5. Validate and Iterate

After implementation, validate against the spec. Use an adversarial agent pattern: one agent implements, a separate agent verifies. The implementor optimizes for completing the task; the verifier optimizes for finding failures. This tension produces better outcomes.

### 6. Replan

Before jumping to the next feature, pause. Revisit the constitution. Check if priorities shifted. Update the roadmap. This replanning phase is where humans provide the most value: architectural thinking, not code writing.

## GitHub Spec Kit: SDD in a Box

GitHub's [Spec Kit](https://github.com/github/spec-kit) is the most practical way to start with SDD. It is an open-source toolkit (111k+ stars, 30+ agent integrations) that scaffolds the entire SDD workflow into your project.

![GitHub Spec Kit repository](/images/blog/spec-driven-development/spec-kit-repo.png)

### Installation

```bash
# Requires uv (Python package manager)
uv tool install specify-cli --from git+https://github.com/github/spec-kit.git
specify version
```

### Initialize Your Project

```bash
specify init my-project --integration copilot
# Or in the current directory:
specify init . --integration claude
```

This creates a `.specify/` folder with templates, scripts, and agent-specific command files. Spec Kit supports Claude Code, GitHub Copilot, Cursor, Codex CLI, Gemini, Kiro, opencode, and 25+ other agents.

![Spec Kit initialization and slash commands](/images/blog/spec-driven-development/spec-kit-workflow.png)

### The Slash Command Workflow

After initialization, your coding agent gets access to structured SDD commands:

| Command | Purpose |
|---|---|
| `/speckit.constitution` | Create project governing principles |
| `/speckit.specify` | Define what to build (requirements and user stories) |
| `/speckit.clarify` | Clarify underspecified areas before planning |
| `/speckit.plan` | Create technical implementation plans |
| `/speckit.tasks` | Generate actionable task lists |
| `/speckit.implement` | Execute all tasks against the plan |
| `/speckit.analyze` | Cross-artifact consistency analysis |

### Step-by-Step: Building with Spec Kit

**Step 1: Constitution**

```
/speckit.constitution Create principles focused on code quality,
testing standards, UX consistency, and performance requirements.
```

This creates `.specify/memory/constitution.md` — the foundation every subsequent spec references.

**Step 2: Specify the Feature**

```
/speckit.specify Build a task management app with Kanban boards.
Users can create projects, assign tasks, drag-and-drop between
columns, and leave comments. No auth for this MVP phase.
```

Be explicit about **what** and **why**. Do not mention the tech stack yet.

**Step 3: Clarify**

```
/speckit.clarify
```

This runs a structured questionnaire that fills gaps in your spec. Run it before planning to reduce rework.

**Step 4: Plan**

```
/speckit.plan Use Next.js 15 with App Router, PostgreSQL via Prisma,
and Tailwind CSS. Deploy to Vercel.
```

Now specify the tech stack. Spec Kit generates a `plan.md`, `data-model.md`, `research.md`, and API contracts.

**Step 5: Tasks**

```
/speckit.tasks
```

Breaks the plan into ordered, actionable tasks with dependency markers and parallel execution hints.

**Step 6: Implement**

```
/speckit.implement
```

Executes tasks in order, respecting dependencies. The agent references the constitution, spec, and plan throughout.

### Customization: Extensions and Presets

Spec Kit is not rigid. Two customization mechanisms let you adapt it:

- **Extensions** add new capabilities (Jira integration, security review gates, domain-specific workflows).
- **Presets** override existing templates and terminology (compliance-oriented formats, domain-specific language, organizational standards).

Multiple presets can be stacked with priority ordering. Project-local overrides allow one-off adjustments without creating a full preset.

## The Adversarial Agent Pattern

One of the most powerful patterns in SDD is assigning separate agents to check work:

![Coordinator, Implementor, and Verifier agent pattern](/images/blog/spec-driven-development/adversarial-pattern.png)

1. A **Coordinator** breaks down the spec and delegates tasks.
2. **Implementor** sub-agents work from sub-specs.
3. A **Verifier** agent checks output against the spec before marking work complete.

The implementor and verifier have opposing goals. One optimizes for completing the task; the other for finding failures. This pattern forces specs to contain explicit verification criteria, which improves the specs themselves.

Model tiering matters here: use your most capable model for writing specs (errors propagate downstream), a mid-range model for implementation, and a fast model for verification.

## When to Use SDD (And When Not To)

SDD has overhead. Not every task justifies it.

**Write a spec when:**
- Work spans multiple agent sessions
- Multiple services or repositories are involved
- Reversing a wrong interpretation is expensive
- Compliance or audit trails are required
- Review requires real attention (component logic, end-to-end flows)

**Skip the spec when:**
- Work is exploratory or experimental
- A single prompt produces usable output
- Output can be reviewed in under five minutes
- The prototype is meant to be thrown away
- The change is mechanical or low-risk

The rule of thumb: if you would be annoyed to have the agent misinterpret your requirements, write the spec.

## Limitations and Open Questions

SDD is not a silver bullet. Key concerns:

**Review overload.** Spec Kit can create 8+ markdown files for a single feature. Reviewing markdown can be more tedious than reviewing code. An effective SDD tool must provide a good spec review experience.

**False sense of control.** Larger context windows do not mean the agent will follow every instruction. Agents ignore specs, hallucinate requirements, and go overboard following others. Small, iterative steps remain the best control mechanism.

**One workflow for all sizes?** Current tools lack flexibility. Kiro turns a small bug fix into 4 user stories with 16 acceptance criteria. Spec Kit creates extensive documentation for a 3-point story. Effective SDD needs workflows calibrated to problem size.

**Spec maintenance.** Keeping specs synchronized with evolving codebases is unsolved. Spec Kit creates branches per spec, suggesting specs live for the lifetime of a change request, not a feature. The community is actively debating this.

**Brownfield adoption.** Applying SDD to existing codebases requires reverse-engineering specs from legacy code. This is categorically harder than greenfield SDD and few tools address it well.

## The Bottom Line

Spec-Driven Development is the natural evolution of AI-assisted coding. Vibe coding proved that LLMs can generate code. SDD proves that without specifications, the code they generate is not trustworthy at production scale.

The methodology is still maturing. Definitions are fluid. Tooling is evolving rapidly. But the core insight is sound: **the spec is the new source of truth**, and the engineer's role shifts from writing code to writing specifications, reviewing architecture, and orchestrating agents.

Start with Spec-First on a single feature. Use GitHub Spec Kit to scaffold the workflow. Graduate to Spec-Anchored as your team builds confidence. And remember: the goal is not to write more documentation, but to write the right documentation that prevents the most expensive failures.
